# Technical Debt

This file tracks known issues, limitations, deferred work, and cleanup items that agents and developers should account for when changing DashVim.

## Known Items

- Agentic review submission uses the pinned session manager's private `_handle_input_submit` method because this version exposes no public prompt submission API. Verify it when updating the plugin. Latest-session restore depends on provider support for ACP session listing/loading and selects from the returned page; the pinned client's list API exposes no pagination cursor.

- Model-free tests validate both configuration transports, strict CLI parsing, and native tools. Authenticated ACP/99 coverage is opt-in (`tests/codex-benchmark.py`); normal checks cannot verify model behavior or service latency. Interactive Agentic widget delivery remains a separate smoke test.
- Read-only approval overhead is fixed using per-tool preapproval with an explicit ACP `agent` mode. Edits still invoke automatic review and can incur retries or variable service delay (roughly 10–14 seconds in the final three-run benchmark). Keep workspace-write confinement; changing to "Full access" is not an equivalent latency fix.
- Scoped developer instructions explicitly exempt focused editor requests from global documentation chores. Global `~/.codex/AGENTS.md` is still discovered and contributes context. This is instruction precedence, not filesystem isolation; recheck authenticated fixtures when Codex or instruction handling changes.
- The pinned MCP server broadcasts events through a Neovim RPC path that crashed Neovim 0.12.5 with five clients. DashVim patches notifications to target each RPC channel individually and covers multiple clients locally. Revisit the workaround after upstream Neovim/MCP fixes.

- README keybinding documentation says it may be outdated. Verify default keymaps in code before changing or relying on README keybinding tables.
- `programs.dashvim.opencode.config` is merged after generated defaults. If a user sets `instructions`, it can replace generated instruction paths such as `AGENTS.md` and bundled skills.
- Generated opencode files are reproducible but not hot-reloaded. Wrapped opencode and Home Manager users must rebuild or redeploy, then restart opencode after config inputs change.
- Home Manager deployment for `opencode/themes/dashvim.json` uses `lib.mkDefault`; user-managed files or higher-priority config can still override DashVim's generated theme/background behavior.
- The `programs.dashvim` option surface is broad. Default changes can affect many editor, language, formatter, and opencode behaviors at once.
- Automated testing is primarily Nix-focused, with a targeted live integration test for the Codex MCP bridge. General Lua plugin behavior and interactive Neovim workflows still lack broad automated coverage.
- `programs.dashvim.toolchain.preferProjectTools` covers known DashVim/nvf LSP, formatter, and linter names. Custom direct `vim.lsp.servers`, conform formatter, or nvim-lint linter names still need explicit command configuration until a public extension map exists.
- `programs.dashvim.lsp.special.roslyn.filewatching` defaults to `"off"` to prevent Roslyn or Neovim from recursively watching too much of the filesystem. DashVim adds a scoped client-side watcher (`vim._watch`) over the solution dir with churn directories excluded (`bin`/`obj`/`.git`/`node_modules`/`.vs`/`.roslyn-cache`/`.generated`), reconciling creates against a known-file set so externally-created project files are delivered as `Created`. This uses the internal underscore-prefixed `vim._watch` API (the same subsystem Neovim's own LSP watcher uses); it is wrapped in `pcall` and silently degrades to save-time-only notifications if that internal API changes. Watch depth/scope is bounded by the resolved solution root (`/` is refused), so a `broadSearch` miss or a top-level solution still never watches a home folder.
- `typescript-tools.nvim` does not expose a first-class plugin probe path option, so DashVim patches its generated process arguments to make Nix-provided `@angular/language-service` discoverable by tsserver. Revisit this if upstream adds `tsserver_plugin_probe_locations` or equivalent.
- nixpkgs `typescript` is now 7.x (Go-native, `tsc` only, no `tsserver.js`): the editor TS stack in `config/languages/lsp.nix` (`pinnedTsserverPath`, `typescriptRoot`) is pinned to `pkgs.typescript_5` (5.9.3, classic JS build) so `typescript-tools.nvim` and `ngserver` keep working. The CLI/toolchain `tsc` fallback (`lib/toolchain.nix`) stays on TS 7, so editor (5.9.3) and CLI typecheck versions can skew — harmless in practice since `preferProjectTools` (default `true`) resolves project-local TS first. Revisit native `tsc --lsp` migration when `@angular/language-service` supports TS 7 or `typescript_5` disappears from nixpkgs; migration means losing all tsserver plugins (Angular/styled/effect/eslint) since the native server has no plugin mechanism.

- `csharpier` formatter (CSharpier 1.x CLI) throws `ArgumentNullException (directoryPath)` when invoked with an empty `--stdin-path`, which happens for unnamed/scratch C# buffers: conform substitutes `$FILENAME` unconditionally (`runner.lua`). Named buffers are unaffected. Upstream would need an empty-path guard; alternatively drop `--stdin-path` at the cost of config-discovery precision.
- ThePrimeagen/99 is pinned to rev `c174224` in `config/editor/ninetynine.nix`. 99 has no tagged releases; re-pin periodically to pick up upstream fixes. The `<leader>nm`/`<leader>np` model/provider pickers assume the telescope extension (`99.extensions.telescope`); fzf-lua users get no 99 picker keybind by default.
- 99's `buildVimPlugin` sets `doCheck = false` because upstream `lua/99/editor/lsp.lua` requires a nonexistent `99.editor.treesitter` module, failing nixpkgs' neovim require-check. Remove once upstream fixes it.
- `flake.nix` `customConfig` (the `minimal` package) overrides `agent`/`lsp` wholesale, so new subtrees (`agent.ninetyNine`, `lsp.tailwind`, `lsp.special`) must be re-inherited from `orig.config.programs.dashvim` explicitly or the minimal build breaks with missing attributes.
- When `ninetyNine.model` is null and OpenCode is selected, 99 uses `opencode/big-pickle` because 99's hardcoded OpenCode default (`opencode/claude-sonnet-4-5`) is not a valid model id and fails every query. Free-model availability rotates, so re-check with `opencode models` if queries start failing again; the runtime picker (`<leader>nm`) lists what is actually available for OpenCode.
- 99 has no built-in Codex provider or Codex CLI model-list API. The local provider uses shared defaults and the local model cache; that cache may be absent or stale. Explicitly configured model IDs are not validated against account entitlement. Both Codex hosts require `codex login`.
- Native ACP filesystem forwarding remains unavailable in the pinned adapter; buffer mutations use the MCP bridge with native undo rather than ACP patch previews. The focused edit tool only writes inside the editor cwd, including new files in existing directories; directory creation and broader filesystem operations require separate user action. Generic Lua and disk-read tools remain upstream administrative tools but are excluded from the model allowlist. Source-less diagnostics and atomic conflict checks are now covered by local tests.

## Maintenance Rules

- Add newly discovered issues here when they are not fixed in the same change.
- Remove or update entries when debt is fixed or no longer accurate.
- Link debt to concrete files, options, or commands when possible.
